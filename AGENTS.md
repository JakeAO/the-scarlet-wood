# AGENTS.md - Guidelines for Agentic Coding

## Project Overview
This is a Jekyll/GitHub Pages static site for "The Scarlet Wood" TTRPG campaign hub. Focus on content workflows, Jekyll collections, and markdown files—not application code.

## Build Commands
```bash
# Install dependencies
bundle install

# Local development (with live reload)
bundle exec jekyll serve --livereload

# Production build
bundle exec jekyll build

# Build with GitHub Pages baseurl
bundle exec jekyll build --baseurl /your-repo-name
```

**Note:** No automated test suite exists. Verify content manually by:
1. Running local dev server and checking rendered pages
2. Testing all internal links work
3. Validating front matter renders correctly

## Linting and Formatting
```bash
# Format markdown with Prettier (install globally or via npx)
npx prettier --write "**/*.md"

# Lint markdown with markdownlint (install globally)
markdownlint "**/*.md"
```

### Configuration Files
- `.prettierrc`: 100 char width, 2 spaces, LF line endings, proseWrap: always
- `.markdownlint.json`: Line length 100 (exceptions for code blocks/tables)
- `.editorconfig`: UTF-8, LF line endings, trim trailing whitespace

## Code Style Guidelines

### File Naming
- Use **kebab-case** for all markdown files: `session-01-northern-border-patrol.md`
- Collection directories: `_info/`, `_world/`, `_sessions/`, `_gm/`
- Images: `assets/images/` with descriptive names

### Front Matter (Required for all collection files)
```yaml
---
layout: page
title: Title Case Display Name
summary: One-line description
topic: Category Name  # for world/info pages
tags:
    - tag-name
index: 1  # sessions only (integer, determines order)
act: 1    # sessions only
published: false  # remove when ready to publish
---
```

### Markdown Formatting
- **Headings:** ATX style (`#`, `##`), one H1 per file matching title
- **Code blocks:** Fenced with triple backticks (\`\`\`), specify language
- **Inline code:** Backticks only
- **Line length:** ~100 characters (soft wrap)
- **Indentation:** 2 spaces for lists and content
- **Lists:** Ordered for steps, unordered for points
- **Links:** Use Jekyll's `relative_url` filter for internal links

### Link Patterns
```markdown
# Internal links (always use relative_url)
[Link Text]({{ "/path/to/file/" | relative_url }})

# Back to collection index
Back to [World]({{ "/world/" | relative_url }})

# Link to image
![Alt Text]({{ "/assets/images/filename.png" | relative_url }})
```

### Naming Conventions
- **Titles:** Title Case (e.g., "The Deep-Root Kin")
- **Topics:** Title Case category names (e.g., "Factions", "NPCs")
- **Tags:** kebab-case (e.g., "antagonist", "forest-kin")
- **Session index:** Integer, sequential (1, 2, 3...)

## Project Structure
```
/
├── _config.yml          # Jekyll config, collections, permalinks
├── index.md             # Home page
├── world.md             # World collection index (grouped by topic)
├── info.md              # Info collection index (grouped by topic)
├── sessions.md          # Sessions index (sorted by index)
├── _world/              # Published player-facing content → /world/:path/
├── _info/               # Published info content → /info/:path/
├── _sessions/           # Published session summaries → /sessions/:path/
├── _gm/                 # Private GM notes (output: false)
├── assets/images/       # Images referenced via relative_url
├── content-templates/   # Article templates for new content
└── .github/workflows/   # CI/CD for GitHub Pages
```

## Collections and Permalinks
- **info:** `/info/:path/` - Campaign rules, custom rules, Utopia system
- **world:** `/world/:path/` - Player-facing lore (NPCs, factions, enemies)
- **sessions:** `/sessions/:path/` - Session summaries, ordered by `index`
- **gm:** Not published - GM-only notes
- **assets:** `/assets/:path/` - Static assets

## Content Organization
- **world.md** and **info.md:** Use Liquid `group_by` on `topic` field
- **sessions.md:** Sort by `index` field (ascending integer)
- Required front matter fields are set in `_config.yml` defaults:
  - `layout: page`
  - `toc: true` (for info/world/sessions)
  - `published: false` (for gm)

## CI/CD (GitHub Actions)
- Triggers on push to `master` branch
- Ruby 3.1, runs `bundle exec jekyll build`
- Deploys to GitHub Pages via Actions
- Build command: `bundle exec jekyll build --baseurl "${{ steps.pages.outputs.base_path }}"`

## Important Constraints
- **Never edit `_site/`** - Generated by Jekyll
- **GM content** in `_gm/` stays private (excluded from build)
- **All images** must use `relative_url` filter for GitHub Pages compatibility
- **Don't modify** `.github/`, `Gemfile`, or `_config.yml` without understanding impact
- **Front matter** must be valid YAML - indentation matters (2 spaces)

## Liquid Template Patterns
When editing index pages or templates:
- Use `| relative_url` for all internal links
- Use `{% for post in site.world %}` for collection iteration
- Use `| group_by: 'topic'` for category grouping
- Use `| sort: 'index'` for session ordering

## Adding New Content
1. Copy template from `content-templates/`
2. Place in appropriate collection directory (`_world/`, `_info/`, `_sessions/`)
3. Set front matter: `title`, `summary`, `topic`/`index`, `tags`
4. Write content using markdown conventions
5. Add internal links using `relative_url` filter
6. Set `published: false` while drafting, remove to publish
7. Test locally: `bundle exec jekyll serve --livereload`

## Common Gotchas
- Missing `topic` field → item won't appear in grouped index
- Non-numeric `index` on sessions → won't sort correctly
- Direct paths without `relative_url` → broken links on GitHub Pages
- Editing `_site/` → changes overwritten on next build
- GM files in `_gm/` excluded from build but visible in repo (if public)

## Agent Design Notes
- When assisting with content creation, follow the established conventions strictly.
- Always validate front matter and markdown formatting before finalizing content.
- Ensure all internal links use the `relative_url` filter to maintain compatibility with GitHub Pages
- When adding player-facing content, always update corresponding DM-facing content in `_dm/` if necessary. Specifically, ensure that any lore or rules changes that become public are removed from the DM notes.
- When generating new content, always consult the existing DM-notes in `_dm/` to get ideas.
